# Nosso Grande Dia — Production Recovery and Commercialization Prompt

## Mission

Act as the lead of a senior multi-agent product engineering team and repair the existing **Nosso Grande Dia** repository and deployed application until it is a genuinely production-ready, commercially viable Brazilian wedding-management SaaS. This is an implementation task, not an audit, mockup, UI refresh, documentation-only exercise, or permission to declare success based on a passing build. Inspect the current code, Git history, Supabase project, migrations, storage, environment configuration and live Vercel deployment; preserve the elegant marsala, off-white and graphite identity, but replace every simulated workflow with secure, persistent, testable behavior.

## Mandatory Multi-Agent Execution

Use specialized agents in parallel with non-overlapping ownership: **Agent 1 — Auth and Security** owns Supabase Auth, SSR sessions, middleware, route/API protection, RBAC, RLS, storage policies and tenant attack tests; **Agent 2 — Data and Product Workflows** owns the database model, persistent CRUD and all wedding modules; **Agent 3 — Billing, Legal and Operations** owns subscriptions, entitlements, LGPD, support and operational readiness; **Agent 4 — Frontend and Accessibility** owns responsive UX, forms, dialogs, empty/loading/error states, SEO and WCAG 2.2 AA; **Agent 5 — Independent QA/Error Hunter** must review the integrated result without trusting commit messages, test every route and control in a fresh browser, attempt unauthorized and cross-tenant access, and report failures to the implementation agents. A lead integrator must inspect every agent’s diff, resolve conflicts and reject mocks, swallowed errors, unsupported claims and incomplete flows. Do not let multiple agents claim the same unfinished area, and do not mark the project complete until the independent QA agent passes all acceptance gates below.

## Verified Current Failures That Must Be Repaired

Treat these as confirmed defects, not optional suggestions: authentication is currently fake because the Zustand store accepts any non-empty email/password, creates a local user, sets authenticated state before Supabase responds and ignores authentication failure; signup marks email as verified immediately; passwords, recovery, deletion and verification are simulated; private pages such as `/orcamento` are accessible without authentication and show the full administrative shell while the header still displays “Entrar”; there is no authentication middleware or server-side route guard; Zustand/localStorage remains the main source of truth and creates browser-bound workspaces instead of durable tenant data; `SupabaseService` covers only fragments of tables/guests, does not await critical calls and silently falls back after errors; the current RLS migration enables RLS without complete policies for memberships and households, has an unsafe/circular workspace bootstrap and permits `FOR ALL` access to demo workspaces; billing is client-side `useState` with hardcoded invoices, fake upgrades/cancellation and `alert` downloads; documents have no real upload, private storage, signed URL or functional download; the latest “productization” commit changed only a small group of presentation files while most modules remained incomplete; tests validate the local mock store rather than real Auth, RLS, persistence, billing or tenant isolation; the live site still contains “Planos Commercias,” duplicate H1s, forms without `name`/`autocomplete`/proper constraints, no canonical URL or Open Graph image, and unsupported claims such as end-to-end encryption, total LGPD/GDPR compliance and “100% secure and certified”; “Nosso Grande Dia Tecnologia Ltda.” and `@nossograndedia.com.br` contacts must not be presented as real unless the owner supplies and verifies the legal entity, CNPJ, address, domain and working mailboxes.

## Non-Negotiable Engineering Corrections

Implement real Supabase authentication using the supported Next.js App Router SSR/cookie flow, server-validated sessions and protected route groups; add middleware and server guards so every private page, route handler, server action, export and file request redirects or returns 401/403 when appropriate; login must succeed only after Supabase returns a valid session, unknown users or wrong passwords must fail, signup must persist only the Supabase user, email verification must be real, recovery must use expiring tokens, logout must revoke/clear the session, and sensitive account operations must require recent authentication. Remove localStorage users and never use Zustand as authoritative persistence; Zustand may hold temporary UI state only. Every mutation must be validated on the server, awaited, persisted to PostgreSQL, return an explicit result and surface recoverable errors; remove silent “graceful” fallbacks that disguise failed writes. Create complete migrations for every production entity and relationship, use UUID tenant/workspace keys and foreign keys, add timestamps and indexes, and implement strict RLS with explicit SELECT/INSERT/UPDATE/DELETE policies and WITH CHECK rules. Solve initial workspace ownership atomically through a secure transaction, trigger or security-definer RPC with a restricted search path; add policies for memberships, households and every current/future tenant table; make demo data a separate resettable read-only environment and never grant public `FOR ALL` access to its database rows. Implement private Supabase Storage buckets and policies for contracts, payment receipts, moodboards, attire, venue files and floor plans; validate MIME type, extension and size, generate expiring signed URLs and record file access. Keep all secrets server-side, remove production fallback credentials from source, validate required environment variables at startup and never commit service-role keys, payment secrets or tokens.

Implement persistent CRUD and real business rules for onboarding, checklist, contingency, guests/households/companions, invitations and RSVP, team and granular roles, budget/items/installments/payments/receipts, suppliers/quotes/contracts, documents and optional AI analysis, style/moodboard, attire, decoration, venues, ceremony/reception, Day-H timeline, seating/floor plan, wedding-site builder, civil marriage, notifications, audit logs, settings, account lifecycle and post-wedding workflows. Real accounts must begin with empty collections and user-provided data; generic sample data may appear only after explicitly entering Demo Mode. Search the repository, migrations, storage and seeds and remove all personal references including Matheus, Virginia, Virgínia, Mendes, Sousa, MV, Campos do Jordão, Quinta das Flores, 2026-11-14 and token-demo-123. Complete forms with the fields already promised by each table and screen, plus create/edit/delete/archive, validation, search, sorting, filtering, pagination, bulk actions, loading, empty, success and error states; every visible button must perform a real authorized operation. Do not use hardcoded arrays, fake dates, `alert()`, artificial delays, client-only success flags, “coming soon,” dead buttons or placeholder downloads as substitutes for implementation.

Implement real subscriptions through one configured payment provider suitable for Brazil, using server-created checkout/customer sessions, webhook signature verification, idempotent event processing, persisted subscriptions/invoices, trial start/end, payment methods, upgrade/downgrade, cancellation, renewal, failed-payment recovery and server-enforced entitlements. Keep plan definitions in one source of truth, currently Starter R$0, Pro R$89.90/month with a 14-day trial and Assessoria R$199/month, but never display an active subscription, invoice or successful payment unless returned by the payment provider and database. When payment credentials are absent, show a truthful disabled configuration state instead of fabricated billing data.

Make document upload and download real; preserve original metadata, versions and access history, use signed URLs, allow authorized deletion/restoration and implement malware-scanning integration or a clearly documented quarantine workflow. Any AI contract analysis must be opt-in, disclose the provider and data handling, quote the source clauses, expose confidence/limitations and never pretend to replace legal review. RSVP must use opaque high-entropy invitation tokens, expiration/revocation, rate limiting, household and individual responses, companions, ceremony/reception attendance, dietary/accessibility information, updates, confirmation and privacy consent without exposing administrative data. Seating must persist draggable coordinates, rotation, table capacity and seat assignments, support move/swap/unassign, household constraints, undo/history, final locking and export. Notifications and audit logs must be database-backed; audit events must cover authentication, permissions, CRUD, files, exports and billing and must not be editable by ordinary workspace users.

Remove every unsupported marketing or legal statement. Do not claim end-to-end encryption, AES-256, TLS 1.3, certification, perfect security, total LGPD/GDPR compliance, legal-company status or operational support channels without verifiable evidence supplied by the owner. Use accurate wording about the actual controls implemented. Replace “Planos Commercias” with “Planos Comerciais.” Do not invent a company, CNPJ, physical address, domain, email or phone; use clearly marked configuration variables or request owner-supplied legal information. Expand Terms, Privacy and Cookie documents only from confirmed operator data and include controller identity, purposes, legal bases, retention, processors, international transfers, cookies, analytics consent, user rights, deletion/export procedures and versioning. Keep personal-data exports authenticated and authorized.

Fix semantic structure and accessibility throughout: exactly one meaningful H1 per page, explicit labels, `name`, autocomplete, input modes and validation constraints, accessible error summaries, dialog roles and labels, focus trap/restoration, keyboard operation, visible focus, contrast, reduced motion and responsive behavior targeting WCAG 2.2 AA. Add route-specific metadata, real canonical URLs matching the deployed/custom domain, Open Graph and Twitter images, sitemap, robots and noindex rules for private and tokenized pages. Eliminate hydration nondeterminism and verify that React errors 418, 423 and 425 do not return. Keep timezone-aware dates using IANA timezone identifiers and avoid server/client locale mismatches.

Run migrations against a clean test database, prove every RLS policy with positive and negative cases, run all scripts and record exact results. Inspect all application routes in a fresh signed-out browser and again with authorized roles; inspect console and network failures; verify every button, form, modal, export and download. Deploy the final commit to Vercel, verify the production URL—not only localhost—and confirm the deployed commit SHA matches the reviewed code.

Do not describe local state as multi-tenancy, a robots rule as route security, UI plan toggles as billing, a static document card as storage or a hardcoded log array as auditing. Completion requires evidence that real authentication, server authorization, database persistence, RLS isolation, storage protection, billing integration and the core workflows work end to end. Finish with a concise report listing agents and ownership, changed files, migrations, environment variables, external services, deployed commit/URL, test commands and results, RLS attack results, routes manually verified and any remaining blockers. If credentials, legal details or external-provider configuration prevent a feature from being completed, report it honestly as blocked and leave a safe non-deceptive state; never replace it with fake production behavior.
